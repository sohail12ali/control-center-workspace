# Decisions: T-004

## entry-point-plugin-shape
**Decision:** T-004's HTTP surface is one new plugin module, `console/server/features/assistant_feature.py`, registered as a tenth `plugins.toml` row, exposing exactly the routes named in the plan: `POST /api/assistant/say {text, source, wait_ms?}`, `GET /api/assistant/session`, `POST /api/assistant/new {backend?, model?}`, `GET /api/assistant/stream` (SSE), `GET`/`POST /api/assistant/memory` — modeled on `verbs_feature.py`'s route-dispatch shape. `httpd.py` is untouched.
**Rationale:** Plan.md:145 ("Entry point") names this exact route list and states the Rust bridge (T-005) and `assistant.js`'s palette box both post to the same `say` endpoint regardless of which tab is showing — one entry point, not one per caller. Plan.md:179 ("Files") confirms `assistant_feature.py` as the new module and names `verbs_feature.py` as its template, and lists `httpd.py` explicitly under "Untouched." This follows the existing plugin contract (CANONICAL: no bespoke second registration mechanism).
**Impact:** FR-1 (routes + plugin registration), FR-10 (CLI reuses the same `say` path). §9 Interactions has no row for this since it is net-new isolation, not reuse of a live mechanism.

## persona-console-owned-second-root
**Decision:** The assistant's persona lives in a new committed file, `console/config/assistant.md` (≤4,000 chars), not under `.claude/agents/`. `prompt_build.persona_text` (`prompt_build.py:56-60`) gains a second root, `console/config/personas/`, so this file is found alongside the existing `.claude/agents/%s.md` mechanism without replacing it.
**Rationale:** Plan.md:149 defines the persona's content (role, reply contract, tool preferences, safety list, known fast commands) as console-owned, not agent-owned — the assistant is explicitly "one ordinary chat plus a dispatch table" (BR-3), never an 8th agent file. Plan.md:151 names the exact plumbing: `persona_text` second root, `system_append` passthrough through `agent_manager.create → agent_session → Backend.session_argv`, per-backend injection mechanism (claude via `--append-system-prompt`, `openai_api` via `extra=`, cursor-agent via prompt-prepend).
**Impact:** FR-3 (injection mechanism per backend), BR-3, BR-7 (4,000-char cap enforcement). Rejected alternative: reusing `.claude/agents/` for the persona — would require a synthetic 8th agent file, explicitly rejected by CLAUDE.md's "Exactly 7 agents" rule and analysis.md:230-232.

## kickoff-as-verb-not-agent-turn
**Decision:** `kickoff` is implemented as a new `verbs.toml` row with a handler in `console/server/kickoff.py` — computing `next_ticket_id`, calling `tickets.create`, rendering `_template/*.md` via the existing `New-FromTemplate.ps1` (never a Python port), and appending the artifact-map row — not as a full agent turn.
**Rationale:** Plan.md:171 states this explicitly: "Rejected: a full `/kickoff` agent turn for a deterministic 1-second job; a Python port of the template substitution (second implementation)." A deterministic, sub-second, template-driven job gains nothing from spinning up a model turn, and porting `New-FromTemplate.ps1`'s substitution logic to Python would create a second implementation of the same behavior (CANONICAL: one fact, one file/script).
**Impact:** FR-6, BR-5 (the verb must mirror the `kickoff` skill's 3 steps, never a thin wrapper around `tickets.create` alone). Edge case: PowerShell-unavailable fallback sends `/kickoff {id} --title …` to the chat instead (plan.md:171), which *is* the one place an agent turn is used, but only as an honest fallback, not the primary path.

## fast-command-table-scope-br1
**Decision:** `say`'s dispatch is a deterministic, normalise-then-whole-utterance-match table (11 rows: new chat/stop/mute/use backend/status/what's-open/create ticket/copy that/remember/do-fix-build-run/screenshot, else → `agent_manager.send`) run before any model call. Codified as **BR-1**: exactly one table match OR one `send`, never both, and no code path inspects a model's output to pick a next action ("no second orchestrator").
**Rationale:** Plan.md:147 states BR-1 verbatim ("`say` = one regex match or one `send`; nothing inspects model output to choose a next step") and plan.md:154-169 gives the exact table, matching rule (whole-utterance only, so "stop the server" is not an interrupt), and normalisation rule (strip wake word/punctuation, `t[- ]?(\d+)` → `T-00N`). `telegram_bot.py:_dispatch` (`:295-378`) is the proven structural template for this one-match-or-fallback shape.
**Impact:** FR-5 (the table itself), FR-2 (BR-1's regression-test AC added at enrich: a fake `send()` returning fast-command-shaped text must never re-enter the dispatcher).

## settings-backend-picker-local-first-default
**Decision:** `console/config/assistant.toml`'s `backend` field is a picker of enabled+installed backends only; its initial (no-prior-write) default is the first enabled+installed backend in **local-first order**, read from `agents.toml`'s existing backend ordering.
**Rationale:** Plan.md:173 ("Backend Settings") states this exact default: "`backend` (picker of enabled+installed backends; initial = local-first order)." Local-first (e.g. ollama/lm-studio before claude/openrouter) matches the programme's stated preference for typed-first, low-cost, offline-capable defaults before cloud backends, and avoids silently defaulting a fresh install to a paid cloud backend with no explicit user choice.
**Impact:** FR-7 (settings route + validation: an unknown/uninstalled backend value is rejected, never persisted), BR-8. FR-7's AC states this default explicitly ("first enabled + installed backend, local-first per `agents.toml` local-first order").

## memory-location-and-caps
**Decision:** All assistant memory — session pointer (`session.json`), capped fact store (`memory.md`, ≤1,500 chars, oldest-first trim), and last-reply file — lives under `console/.cache/assistant/`, already covered by the blanket `.gitignore:65-67` rule. No code path in this ticket writes to `knowledge-center/` (the Obsidian vault).
**Rationale:** Plan.md:177 ("Memory") states this exactly: "conversation = the chat itself; pointer + `memory.md` + last reply under `console/.cache/assistant/` (gitignored, `.gitignore:67`). No vault writes." Codified as **BR-4**. This keeps the assistant's working state ephemeral/local (consistent with `console/.cache/`'s existing role for `desktop/serve.log`, `host.log`) and never mixes it with the vault's durable, versioned, human-curated artifacts.
**Impact:** FR-9 (memory file mechanics + secret-shaped-fact guard added at enrich), BR-4 (tested via a diff grep confirming no write targets `knowledge-center/`).

## assistant-chat-identity-flag
**Decision:** The Assistant chat is identified to the frontend by one new boolean field, `is_assistant`, added to the existing `session.started` event payload (`agent_session.py:380-385,494`) and threaded through `agent_manager.create(..., is_assistant=False)`. `agents.js`'s `autoRead` handler (`:838-846`) checks `store.state.meta.is_assistant` (the same `meta` object it already reads via `store.on("meta", ...)`, `agents.js:835`) and skips speaking when true, since the new server-side reply watcher (FR-8) already owns speaking for that chat.
**Rationale:** The plan (plan.md:175) states the no-double-speech invariant but not the mechanism; `analyze T-004`'s GROUND pass (analysis.md:263-269) and `challenge-requirements` both flagged this as the ticket's highest-risk unspecified piece. Reusing the existing `session.started`/`meta` channel needs zero new event types or transport — only one boolean field and one guard line — consistent with SIMPLIFY (minimum that works) and CANONICAL (no second identity mechanism for "is this the assistant's chat").
**Impact:** FR-8's flow/AC, the Edge Cases §8 "autoRead double-speech" bullet, and §9 Interactions' "Per-chat autoRead" row all reference this mechanism. No other session type gains the field (defaults `False`), so existing chats are unaffected.

## remember-secret-guard
**Decision:** The `remember {fact}` fast command/verb (FR-6/FR-9) declines to append a fact whose text matches a small set of secret-shaped patterns (`-----BEGIN`, common provider-key prefixes, a bare `KEY=value` line), returning a stated reason instead. This extends `assistant.md`'s persona safety list (plan.md:150) with one more rule to the same effect.
**Rationale:** `challenge-requirements` (COMP-GAP-1) noted `memory.md` is plaintext and re-injected into every future session's `extra` context (FR-4) with no guard against a user asking the assistant to remember a credential. Low severity (single-user local tool, §11 Stakeholders), but a concrete rule is cheap and consistent with the persona's existing safety framing, so it was adopted rather than left as an accepted risk.
**Impact:** FR-9 gained a flow step + AC; §5 NFR Compliance row updated from "none identified" to this rule.
