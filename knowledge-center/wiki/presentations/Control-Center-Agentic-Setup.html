02Problem22

Why this exists

A capable model with no method
is an expensive improviser.

Hand a coding agent a ticket and it will produce something. The question is whether you can tell, six weeks later, what it decided and why — and whether it would do the same thing twice.

  • It fills gaps instead of stopping. Missing scope gets answered confidently rather than asked about.
  • Reasoning evaporates. The plan, the objections and the rejected options live in a chat log nobody re-reads.
  • Facts get re-derived. The same eight artifacts are opened and reduced at the start of every turn, at full token price.
  • "Done" is a claim, not evidence. Nothing forces a build, a test, or a file:line behind the word.

03Idea22

The core idea

The model does not decide how we work.
It follows how we work.

The agent writes the code. It does not choose the order of work, the shape of the files, or the points at which it must stop and ask. Those are fixed in advance and checkable.

So what changes

Same steps every time

Every ticket runs the same six gates in the same order — regardless of who started it, which model answered, or how busy the day was.

So what changes

It stops instead of guessing

Unclear scope halts the run and raises a question. A gap is never filled with a confident-sounding answer.

So what changes

The reasoning survives

Requirements, plans, critiques and decisions are files in a vault — so next quarter you can still find out why.

04Scope22

What it is, and what it is not

A template you drop in —
not a platform you adopt.

  • Project-independent. No company, product or stack is named anywhere in the harness. Sub-projects join as workspace folders, each with its own ticket ids and artifact subtree.
  • Editor-agnostic. The console sits at the workspace root beside .claude/ and .cursor/, owned by neither.
  • Zero runtime dependencies. Stdlib Python, vanilla JS, no build step. pytest is dev-only.
  • Files you can read. Markdown for prose, TOML for state, git for history. No database, no service.
Not this

Not an autonomous developer

The pipeline needs a human at three points: open questions, plan approval, and anything irreversible. It is a method with an engine, not a replacement for judgement.

Not this

Not a hosted product

Everything binds to 127.0.0.1. There is no account, no tenant, and nothing leaves the machine except the model calls you configure.

05Gates22

The method

Six gates. Each one stops the run.

They are loaded into every session, not recited per ticket — a single always-on file small enough to never be skipped.

GateWhat it demandsWhat it prevents
GROUNDSurvey the code and prior artifacts before drafting anythingA requirement invented from the prompt rather than read from the repo
CLARIFYAsk every open question before producing outputAmbiguity resolved silently in the model's favour
CANONICALEvery fact lives in exactly one file; search before creatingThree files that disagree, and no way to tell which is current
TEMPLATEEvery file type derives from a template — stop if none existsArtifacts whose shape drifts per ticket, so nothing can be validated
SIMPLIFYWrite the minimum that worksSpeculative abstraction built for a requirement nobody stated
VERIFYCited evidence behind every "done"; artifacts link up and downA completion claim with nothing behind it

Running across all six: BE HONEST — report outcomes faithfully. If tests fail, show the output. If a step was skipped, say so. Label what is assumed. Surface bad news early.

06Roles22

Who does what

Seven agents, one shared shell.

AgentStagesOwns
harnessallRoutes the ticket. Never does the work itself — delegates, then reconciles.
analystGROUND · CLARIFYAnalysis, requirements, decisions. Drafts, red-teams its own draft, then freezes.
plannerCANONICALFrozen requirements → stories, components, tasks, risks. No code.
builderTEMPLATE · SIMPLIFYOne plan task at a time, then a simplification pass.
verifierVERIFYTest cases, evidence, traceability, artifact integrity — then closes.
fixeranyRoot-cause and minimal patch when something fails mid-flight.
deployerafter closePublish. Always ASK-gated — never triggered by a clean verify.

Exactly seven, by design. A new role is a change to the method, not a convenience — so it needs explicit intent, not a quiet addition.

08Entry22

The free-form entry point

One command. Five lanes. First match wins.

Not every request is a ticket. /do {request} classifies first, then dispatches — so a question does not become a delivery pipeline, and a delivery does not become an improvisation.

If the request…LaneWhat runs
names a ticket id, or is end-to-end deliveryA deliverFull kickoff → the seven-agent route
maps onto one or more skillsB skillThe matched skills, in dependency order
is a whole role-phase with no ticketC roleThat role agent, loaded and run
is read-only — where, why, trace, showD investigateGrep, read, trace — no writes
is a sub-project build, test or publishE cross-repoThat repo's own commands, via its own manifest

Ambiguous lane → ask, never guess. The classifier states which lane it chose, which was runner-up, and why — so a bad route is visible in one line rather than discovered three files later.

09Vault22

Where the work lives

One folder per ticket.
One file per fact.

knowledge-center/artifacts/T-016/
  T-016-summary.md          status, owner, scope
  T-016-analysis.md         ground survey
  T-016-requirements.md     frozen spec
  T-016-decision-log.md     why, + rejected
  T-016-plan.md             tasks, deps, risks
  T-016-progress.md         dated entries
  T-016-verification.md     evidence
  ticket.toml               ← state, CLI only
  T-016-questions.toml      ← tracker, CLI only
  T-016-bugs.toml           ← tracker, CLI only

Flat, not nested. Every file is {TICKET}-{artifact}.md and ends with a ## Links block naming its siblings — which is what makes traceability checkable by a script rather than by reading.

The split that matters

Markdown holds prose

Reasoning, specs, critique. Human-authored, model-authored, diffable, reviewable in a PR.

The split that matters

TOML holds state

Lane, owner, links, open questions, bugs, todos — mutated only through the CLI. Never hand-edited, by a human or an agent.

Why

A status you can trust

If an agent can hand-write the lane, the board is a rumour. One mutation path means the board and the vault cannot disagree.

10Console22

The Delivery Console

One local server.
Every board, every tab.

A web app and a CLI over the same files the agents write. It does not own the data — it is a window onto the vault, not a second copy of it.

  • Boards. Tickets and Investigations on by default; Migrations and Releases ship as config with enabled = false, so a project turns them on without a code change.
  • Tabs. Overview, Agents, Work, Analytics, Todos, Vault, About, Settings.
  • Same state. Board lanes come from the same TOML the CLI mutates. There is no sync step because there is nothing to sync.

11Verbs22

The central economy

Compute, don't reason.

If a question has exactly one right answer and no judgement in it, asking a language model is paying tokens for arithmetic — and arithmetic that can come back subtly wrong.

Model turn

"Which plan tasks are unchecked?"

Reads the plan, reduces it, answers. Costs tokens. May miscount. Answers slightly differently next time.

Verb

console plan-status T-016

Parses the plan in Python. Costs nothing. Same answer every time. Reports what it could not parse rather than guessing.

  • Declared in config, not code. A verb row names a handler as a dotted path; the registry imports it. Adding a verb is one TOML block.
  • Gates travel with the verb. needs_ticket, needs_confirm, which board kinds and lanes — so the CLI, the board, the scheduler and the MCP server all enforce the same rules without reimplementing any of them.
  • Broken handlers fail at startup, named — not at the moment someone finally runs them, which is always the worst moment.
  • Mutating verbs need confirmation. That stops a stray click or a hallucinated tool call — it is not the human approval gate, which lives elsewhere.

13MCP22

How agents reach it

The verbs are the tool set.

Claude Code, Cursor and API-backed agents all need the same thing: to ask the console what it knows instead of reading eight files to work it out. Writing that three times means three surfaces that drift, so it is implemented once as MCP.

Tools

Generated, not listed

There is no tool table in the server. It walks the verb registry and derives each schema from the handler's own signature — so a new TOML row is a new tool with no code change.

Resources

Every ticket is a URI

ticket://{ID} returns the same digest the context verb produces — delegated, never a second representation. Clients can subscribe and be pushed an update when it changes.

Setup

One command per editor

setup cursor|claude|vscode writes that editor's MCP config plus a warning against hand-editing ticket TOML. Idempotent — it merges rather than overwrites.

Deliberately small: three methods plus resources. Prompts, sampling and completion are not implemented, and the server says so through its declared capabilities rather than failing calls at runtime.

The UI reads steerability from the transport and hides the control where the CLI cannot do it — rather than offering a button that lies. An openai_api backend runs the agent loop in-process, which is what lets it hold the console's own verbs as tools and use the same approval gate.

The approval gate

Gated: Bash, Write, Edit, WebFetch, Task, screenshot, clipboard-read

Each raises a "Permission needed" card. Screenshot and clipboard-read are answerable at the desk only — a screenshot sends whatever is on screen; a clipboard read can send a password.

Not gated, on purpose

Reads are free

Asking a human to approve "look up this ticket's lane" trains them to click allow without reading — which is how a gate stops working for the calls that actually matter.

Full-bypass permission modes are deliberately absent. Turning the gate off is a decision for a terminal you are sitting in front of, not a button on a web page.

15Runs22

Concurrency

One isolated checkout per run.

One agent at a time with a human watching is merely untidy. The moment runs are scheduled, queued or triggered remotely, shared working trees become a correctness problem: two agents interleave their edits and nothing records that it happened.

  • Never create over an existing path. Reusing a directory silently inherits whatever the last run left there, half-applied edits included.
  • Never remove a worktree with uncommitted work unless forced — and when refusing, say exactly what would be lost. A run's entire output can be uncommitted.
  • Never guess a branch name. The pattern comes from config, because branch conventions belong to the project, not to the tool.
Read-only hint

PR state via gh

No GitHub client, no token storage. It shells out to a CLI that manages its own auth, parses exactly what is needed, and surfaces a lane hint. It never becomes a second tracker or a write path back to GitHub.

Coordination

ready · claim · comment

An agent asks what is ready, claims it, and reports back — through the same mutation API as everything else. A session stop-hook reminds anyone who claimed a ticket and then recorded nothing.

16Cost22

What it costs to run

Spend is a first-class fact.

Token spend is recorded per run and attributed, so "what did this ticket cost" is a query rather than an argument.

GroupingAnswers
--by ticketWhat has this piece of work cost end to end — and it shows up in the ticket digest, so an agent sees it too
--by modelWhether the expensive model is earning its place against the cheap one
--by skillWhich parts of the method are expensive — the input to trimming them
--by backendLocal vs hosted, in money rather than in impressions
--by dayWhether a change to the harness moved the number

Paired with harness lint and telemetry skills, which report structural breakage across the harness and which skills are actually invoked. A skill nothing calls is evidence it may be dead — reported as a warning, never an error, because a lint that cries wolf gets disabled and then the real errors go unseen too.

17Shell22

Beyond the browser tab

A native shell, and what
a browser tab cannot do.

The console is honest about its own limits: a page on 127.0.0.1 cannot capture the screen, run OCR, drive the mouse, or hold a microphone open. Those need a real host.

  • Tauri 2 host wrapping the same server — it does not replace it.
  • The tray is a remote control for the live chat: show, talk, new chat, mute, interrupt, quit. Built from a feature registry file, not described by one.
  • Local speech. Whisper for listening, Piper for speaking — on the machine, not in a cloud.
  • Never one-click. The tray may open a window or start listening. It may never approve anything.
Status, plainly

Phase 1, and unfinished

The shell is a spike. Hands-free listening was rebuilt this month after the original design proved unusable — it detected the wake word by transcribing every sound in the room and matching text. The rebuild moves detection onto the audio itself.

Not signed off

Three tickets still in Verify

The Assistant, the tray, and hands-free listening are all implemented and none is closed. They are shown here as work in progress, not as capability you can rely on today.

18Adopt22

Getting started

Empty folder to agreed requirements.

$ python console/kanban.py onboard

  1 identity          who is writing the logs
  2 project name      what this workspace is
  3 boards            which kinds are on
  4 agent CLI         which backend
  5 first ticket      kickoff
  6 requirements      missing → stub → drafted → frozen

nothing above writes. every step reports state
and names the command that changes it.

The last step is the point of the list, not an afterthought.

  • It tracks every ticket through missing → stub → drafted → frozen, and names the pre-freeze skill chain — whose order is the part people forget.
  • Nothing is guessed. The remaining work is decisions: what this is called, which boards, what the requirements are. A wizard that guesses at those just produces a workspace somebody has to un-guess.
  • It can be switched off with one config row, once it stops earning its place.
19Evidence22

How we know it holds

The harness checks itself.

Prompt-facing config has no compiler behind it. A skill whose name drifts from its directory, a path reference to a renamed file, a skill nothing calls — all silent, all surfacing later as an agent behaving oddly mid-ticket.

Error — fails CI

Unambiguously broken

A missing frontmatter field. A name that disagrees with its own directory. A path that resolves to nothing. No judgement involved, so no argument about it.

Warning — never fails

Judgement required

An orphan skill is evidence it may be dead, not proof — a skill can be legitimately user-invoked only. Warnings do not fail CI, because a lint that cries wolf gets turned off.

Narrow on purpose

Explicit paths only

It follows real path references, never a bare word in backticks. Guessing at prose produces a false positive on every ordinary noun, and a linter wrong a third of the time is worse than none.

Alongside it: 60 test modules over the console, and a validator that reports the full requirement → task → code → verification chain with coverage percentages — report-only, never modifying files.

20Limits22

Being honest about it

What this does not do.

BE HONEST is a gate in the method. It would be a poor advertisement for it to leave this slide out.

Honest limit

Built and exercised by one engineer

A second concurrent user is unproven and will surface gaps in the conventions that one person never hit.

Honest limit

Three features sit in Verify

The Assistant-as-home model, the tray, and hands-free voice are implemented and unclosed. Implemented is not the same as signed off.

Honest limit

Two boards are stubs

Migrations and Releases exist as config with enabled = false. Projects and Files tabs are not built at all. That is a choice, but it is still an absence.

Honest limit

The gates bind the agent, not you

Nothing stops a human hand-editing a TOML file and desynchronising the board. The discipline is enforced on the automated path, which is where it was being lost.

Honest limit

The desktop shell needs a Rust toolchain

Which works against the drop-in-anywhere property the rest of the template holds to. The web console has no such requirement.

Honest limit

Model quality still varies

The method makes failures visible and recoverable. It does not make a weak model into a strong one.
